# Project Decisions

This document records significant architectural and design decisions made throughout the project's development.

## 2026-08-10: The `postmark` sender guards header structure but does not validate email addresses

While fixing display-name quoting per RFC 5322 (issue #180, PR #182), review found that the email address itself also reaches the `To`/`From`/`ReplyTo` headers verbatim, so a hostile address could smuggle a second recipient or split the header. We had to decide how much the sender should check.

Alternatives considered:

- Full validation with `model.EmailAddress.IsValid()`: rejects all known attack payloads, but also rejects working addresses such as `a@localhost`, internationalised domain names, and address literals — a behaviour change with real breakage risk for consumers.
- Narrow structural guard: reject only characters that can restructure the header (`<`, `>`, `,`, C0 controls, DEL). Everything else passes through as given.

Decision: the narrow guard, and reject rather than sanitise. `createNameAndEmail` returns an error for a structurally dangerous address (`NewSender` panics on a bad configured address, matching the existing fail-fast-on-bad-config pattern), because silently rewriting an address risks delivering to a different mailbox than the caller asked for. The sender deliberately makes no claim about address validity or deliverability — that remains the application's concern. A consequence is mild over-rejection: RFC 5321-legal quoted local parts like `"very,unusual"@example.com` are refused, accepted as the price of one simple rule instead of two.

## 2026-08-24: A client's trace context and baggage never become this service's own

Honeycomb showed every `POST /mcp` server span in production parented to a trace we never see: the client sent `traceparent`, `otelhttp` extracted it, and our main spans dangled off a missing root. One client even grouped two MCP calls and a token refresh under a single trace ID of its own choosing (issue #197). A client outside our control was deciding both the grouping and the sampling of our telemetry.

Alternatives considered:

- Stop configuring propagators globally: kills outbound injection and the enqueue-time trace context the `jobs` queue carries, so a job would no longer join the request's trace. Far too broad.
- `otelhttp.WithPublicEndpointFn` answering true for every request: the literal "every server span is a root" reading. But `trace.WithNewRoot` severs *any* parent in the context, and `otelhttp` links only a parent which is remote, so a span started above the middleware in the same process — another copy of this middleware, a consumer's own tracing middleware, an in-process `ServeHTTP` — would be dropped with nothing recording that it existed.
- Answering true only when the extracted span context is remote.

Decision: the last one. `OpenTelemetry` passes `otelhttp.WithPublicEndpointFn(func(r *http.Request) bool { return trace.SpanContextFromContext(r.Context()).IsRemote() })`, unconditional in the sense that matters — there is no option to turn it off, since no client is trusted enough to parent our spans. A request which brought trace context gets a trace root of its own plus a span link to the remote context, which keeps the correlation available without granting control. A request whose context already holds a local span keeps that span as its parent, because that parent is this process's own and severing it would lose a real connection for nothing.

`otelhttp` v0.65.0 has no plain `WithPublicEndpoint()` any more, only the function form, so the predicate was the available shape regardless.

Baggage is the same problem wearing different clothes, and gets a blunter answer. It is client-controlled key-value state which rides the context into handlers, out through anything the propagator is injected into, and into the job envelopes the queue persists, so a client which sets it writes into places it has no business reaching.

The precise alternative was to discard only the baggage the request carried, preserving any the context already held so that an in-process `ServeHTTP` kept its own. It distinguishes baggage by when it entered the context rather than where it came from, which leaves a hole — tracing above the middleware which extracts baggage itself defeats the discard — and it is machinery for a use nothing has.

Decision: discard all of it. `OpenTelemetry` hands `otelhttp.WithPropagators` a `discardBaggage`, which delegates extraction to the global propagator and then returns the context with no baggage at all. No baggage crosses the HTTP layer, whatever its source, and no hole is left where one source slips through. Because the discard happens during extraction rather than below it, the baggage is gone before the server span starts, so a sampler or span processor does not see it either. `Inject` and `Fields` delegate to the global propagator, since `discardBaggage` has to satisfy `propagation.TextMapPropagator` whole; only extraction changes. Outbound propagation and the queue's enqueue-time trace context go through the global propagator directly and are untouched.

Baggage set while handling a request still propagates from there, but that is a consequence rather than a supported feature. Carrying baggage through the HTTP layer would be a deliberate change to make when something actually needs it.

## 2026-08-26: `oteltest` installs a switchable stand-in, rather than pinning the global OTel defaults once

`oteltest.NewSpanRecorder` set the global `TracerProvider` for a test and restored `otel.GetTracerProvider()`'s prior value in cleanup. That "save, then restore" pattern is unsafe against `go.opentelemetry.io/otel`'s actual global state: its defaults for both the tracer provider and the text map propagator are placeholders that, once any concrete value is ever set, wire their delegate to it permanently for the life of the process. If a helper's "previous" ever turned out to be that raw placeholder (i.e. the helper ran first in a test binary), restoring it would not undo the installation; it would leave the placeholder permanently forwarding to whatever the helper had installed.

We had already hit this for the propagator (`http/otel_test.go`'s `usePropagators`, from the issue-197 work): no shutdown mechanism exists to neutralize a leaked propagator, so that helper always left a known-inert composite behind in cleanup rather than trying to restore "previous". A follow-up review of `oteltest.NewSpanRecorder` found the identical pattern for the tracer provider, unfixed.

A first attempt fixed this by pinning: an unexported `pinGlobals`, a `sync.OnceFunc` that unconditionally installed an inert stand-in (a no-op tracer provider, an empty composite propagator) as the very first `otel.SetTracerProvider`/`otel.SetTextMapPropagator` call in the process, before any helper ever saved "previous". A second-opinion review (external, via the `codex` CLI) found this itself broke valid library usage in two ways CLAUDE.md's "design for correctness across all valid uses of the public API" rule exists to catch: (1) a consumer who configures a real provider or propagator before the first `oteltest` helper runs (in their own `TestMain`, for instance) had it silently destroyed, since the pin overwrote it unconditionally and "restore previous" then restored the pin's own inert value instead of the consumer's; (2) a `trace.Tracer` obtained via `otel.Tracer(name)` and cached before the first helper call — exactly what `jobs.WithTracing` in this same module does at construction time — binds permanently, by the SDK's one-time delegate-wiring, to whatever the pin installed (an inert no-op), so that tracer's spans silently stopped reaching any later `NewSpanRecorder`. The pin traded one invisible hazard for two others.

Alternatives considered:

- Keep the simple pin, since it fixed the originally reported leak: rejected, because it introduced its own silent-breakage modes for valid consumer usage, which is worse than the bug it fixed for a library with unknown, uncontrolled callers.
- Detect "already configured" and skip pinning in that case, but keep a flat no-op/noop-provider swap otherwise: rejected on its own, because it only fixes the "don't destroy a pre-configured value" half (finding 1) — a tracer cached before the first helper call in an otherwise-untouched process would still bind permanently to the flat no-op, since nothing about a plain pinned value can retarget a reference that already resolved against it.
- A "switchable" stand-in: install a small delegating `trace.TracerProvider`/`propagation.TextMapPropagator` that this package owns, once, as literally the only value it ever passes to `otel.SetTracerProvider`/`otel.SetTextMapPropagator`; have every helper swap the stand-in's internal target field instead of calling those functions again. Chosen.

Decision: `oteltest` now has `switchableTracerProvider`/`switchableTracer`/`switchablePropagator` (`oteltest/switchable.go`), each resolving a mutex-guarded `target` live on every call rather than fixing one when first obtained — the property that lets a `trace.Tracer` cached before this package's stand-in was ever installed still follow a later swap, since the SDK's one-time delegate wiring ends up binding such a tracer to the stand-in itself, and the stand-in never stops re-resolving. An unexported `install` (`sync.OnceFunc`) installs both stand-ins on first helper use and never calls `otel.SetTracerProvider`/`otel.SetTextMapPropagator` again; `NewSpanRecorder`/`UsePropagators` swap the stand-in's target instead, a plain, always-safe field assignment regardless of nesting depth or SDK internals. On that first install, `install` compares the current global against a snapshot captured at this package's own initialization (necessarily before any test or a consumer's `TestMain` could have run) to tell a consumer's real pre-configuration apart from nothing having touched the global yet — a real configuration becomes the stand-in's starting target rather than being replaced, fixing finding 1; only a genuinely untouched global falls back to a fresh inert stand-in, and deliberately not to the untouched raw default itself, since using that as the switchable's own target would wire the default to forward into the switchable it is also the target of — an infinite loop.

Each of the four safety properties this design is meant to guarantee (a pre-configured provider/propagator survives; a pre-cached tracer/propagator reference still delivers after a later swap; nested helper calls restore correctly; a pristine process leaks nothing after cleanup) is backed by its own test, including two which re-exec the test binary as a subprocess (`oteltest/pristine_test.go`) since the SDK's one-time delegate wiring can only be observed in a process where nothing has touched it yet, and Go tests can't get that guarantee for themselves once another test in the same binary has run. One residual case is out of reach regardless: a consumer who both caches a tracer/propagator reference *and* configures the real otel globals themselves, before any `oteltest` helper ever runs, has that reference bound to their own configuration permanently — an existing property of the OpenTelemetry API itself, not something a test helper can change, and documented as such rather than left implicit.
