# Diary: Carry a CSP nonce into page rendering (issue #203)

Datastar 1.0.3 has a CSP mode: a `data-nonce` attribute on `html` matching the nonce in `script-src` lets a page drop `'unsafe-eval'`. httph v0.4.0 (httph#29) now generates the per-request nonce when `ContentSecurityPolicyOptions.ScriptNonce`/`StyleNonce` is set and exposes it via `httph.NonceFromContext`. glue owns the page-render half: the nonce has to reach every `PageFunc` call, including error and not-found pages.

## Step 1: Requirements

**Author:** main

### Prompt Context

**Verbatim prompt:** "See issue 203" followed by, one unit at a time: "next", "next", "ok", "move inside", "same group", "in", "go, and also check for 404 outside HTML paths"
**Interpretation:** Refine issue #203 into concrete requirements, then delegate the build. Markus decided: the 404 handler moves into the full HTML group (after all its middleware), the `Cache-Control: no-store` middleware for nonced responses is in scope, and 404s on non-HTML paths must be verified.
**Inferred intent:** Let apps on glue turn on Datastar CSP mode without `'unsafe-eval'`, without any page (including error/404) panicking in `datastar.Nonce`.

### What I did

Read the issue, httph#28, the merged httph#29 (v0.4.0), and glue's `/http/routes.go`, `/http/server.go`, `/http/router.go`, `/http/error.go`, `/http/auth.go`, `/html/error.go`, `/html/common.go`. Created worktree `csp-nonce`. Wrote the requirements below and handed them to a builder.

### Why

The issue's third point (a request-aware `NewServerOptions.CSP`) is moot: httph kept the `ContentSecurityPolicy` signature and put the nonce behind option flags, so apps just set `opts.ScriptNonce = true`. What remains is getting the nonce into `PageProps` everywhere a `PageFunc` is called, and making sure 404s actually run inside the CSP middleware (otherwise the context has no nonce and CSP-mode pages panic).

### Requirements handed to the builder

1. Bump `maragu.dev/httph` to v0.4.0.
2. `html.PageProps` gains `Nonce string`; `http.GetProps` populates it from `httph.NonceFromContext(r.Context())`.
3. `html.ErrorPage(page PageFunc, props PageProps)` and `html.NotFoundPage(page PageFunc, props PageProps)` take props from the caller and override `Title`. Callers: `http.NotFound` (uses `GetProps(w, r)`) and `http.Logout` (passes its props).
4. `r.NotFound(...)` moves into the HTML group in `setupRoutes`, registered after all of that group's `Use` calls, so 404 pages get CSP, clickjacking, session, user and permissions.
5. New middleware in the HTML group: when `httph.NonceFromContext` is non-empty and the response has no `Cache-Control` header, set `Cache-Control: no-store`.
6. Verify 404s on non-HTML paths (arbitrary unmatched paths, paths under the static group, sub-routers mounted by the app) get the same treatment; chi's `NotFound` in a group wraps with that group's middleware and propagates to the parent and sub-routers.

### What worked

Reading httph#29 before forming requirements cut a third of the issue.

### What didn't work

`gh issue view 203` failed once with `read: connection reset by peer`; a retry worked.

### What I learned

chi's `Mux.NotFound` called on an inline (group) mux wraps the handler with the group's middleware chain and installs it on the parent, so "move it into the group" is a one-line change with the right semantics.

### What was tricky

Whether to give 404s the full HTML group (session, auth, permissions) or only the two security middlewares. Markus chose the full group: a 404 page that forgets who you are is worse than an extra `userActiveChecker` call.

### What warrants review

Placement of `NotFound` relative to the `Use` calls in the HTML group; the `no-store` middleware must not clobber a `Cache-Control` a handler set deliberately.

### Future work

None identified yet.

## Step 2: Implementation

**Author:** nonce-builder

### Prompt Context

**Verbatim prompt:** The lead's brief: "Let apps built on glue use Datastar 1.0.3 CSP mode: a per-request CSP nonce must reach every `html.PageFunc` call, including error and not-found pages, and 404 responses must carry the CSP and clickjacking headers." Six numbered requirements followed, covering the httph bump, `PageProps.Nonce`, the `ErrorPage`/`NotFoundPage` signature change, moving `r.NotFound` into the HTML group, a `Cache-Control: no-store` middleware, and verifying 404s on non-HTML paths.
**Interpretation:** Build the glue half of issue #203 in this worktree, with tests, then self-review before handing back.
**Inferred intent:** An app can set `opts.ScriptNonce = true` and every page it renders — matched, errored, or 404 — receives a nonce that matches the header actually sent.

### What I did

Bumped `maragu.dev/httph` to v0.4.0 (its go directive is 1.24, ours is 1.25.0, so no change needed there). Added `Nonce string` to `html.PageProps` in `/html/common.go` and populated it in `http.GetProps` (`/http/router.go`) from `httph.NonceFromContext`. Changed `html.ErrorPage`/`html.NotFoundPage` in `/html/error.go` to take a `PageProps`, override only `Title`, and pass the rest through; updated `http.NotFound` (`/http/error.go`) to build them from `GetProps(w, r)` and `Logout` (`/http/auth.go`) to pass its own props.

Added `NoStoreIfNonce` and its `noStoreWriter` to `/http/middleware.go`, and rearranged the HTML group in `/http/routes.go`. New tests: `/html/error_test.go`, `/http/middleware_test.go`, `/http/routes_internal_test.go`, plus `TestGetProps` in `/http/router_test.go` and `TestLogoutErrorPage` in `/http/auth_test.go`.

### Why

`html.PageFunc` is the only place a page can learn its nonce, and `PageProps` is the only channel into it. The error and not-found pages were building a `PageProps` from nothing, which is why they could never carry one — hence the signature change rather than a second nonce-only parameter.

### What worked

Reading chi's source through `go doc -src -u github.com/go-chi/chi/v5 Mux.NotFound` (and `Mux.With`, `Mux.Mount`) settled the routing question before a line was written. Red/green worked as intended twice: a test written from the brief's wording ("does not set it without a nonce", "works when the handler writes a body without calling `WriteHeader`") failed on a case I had not thought about, and the review's session-cookie test failed on a real bug.

### What didn't work

Two failures worth recording.

The first: `NoStoreIfNonce` set no header at all when a handler returned without writing anything, because nothing ever called through the wrapper.

```
=== RUN   TestNoStoreIfNonce/sets_no-store_where_the_handler_writes_nothing_at_all
    middleware_test.go:35: Expected "no-store", but got "" (type string)
```

Fixed by calling `setNoStore` once more after `next.ServeHTTP` returns: the header map is still open at that point, and the call is a no-op if the handler already wrote.

The second, found by self-review and confirmed with a test written for it:

```
=== RUN   TestSetupRoutes/marks_a_nonced_response_which_writes_a_session_cookie_as_no-store
    routes_internal_test.go:135: Not true
    routes_internal_test.go:135: got Cache-Control no-cache="Set-Cookie"
```

The brief put `NoStoreIfNonce` directly after `httph.ContentSecurityPolicy`, which is *above* `scs`'s `LoadAndSave`. When scs writes a session cookie it also does `Header().Add("Cache-Control", 'no-cache="Set-Cookie"')`, and it does so through the writer of whatever sits above it — us — *before* delegating. So `setNoStore` saw a non-empty `Cache-Control`, took it for the handler's own, and skipped. That silently killed `no-store` on every session-touching response: login, logout, flash messages — precisely the logged-in pages that Datastar CSP mode is for. `no-cache="Set-Cookie"` is the qualified form, which does not prevent storing, so the 304-pairs-old-body-with-new-nonce failure was still live.

Fixed by moving `NoStoreIfNonce` between `LoadAndSave` and `Authenticate`. Both headers then go out (two `Cache-Control` field lines, equivalent to a comma-joined list, and `no-store` wins), and from there it still covers the error responses `Authenticate` and `SavePermissionsInContext` produce. Nothing else in glue writes `Cache-Control`, so nothing else can shadow it.

### What I learned

Requirement 4 as written — move `r.NotFound` from the root into the HTML group — breaks 404s under any sub-router an app mounts. chi's `Mux.NotFound` on an inline group mux installs the wrapped handler on the *parent* and leaves the inline mux's own `notFoundHandler` untouched; `Mux.With` copies the parent's handler at group-creation time; `Mux.Mount` copies the mounting mux's handler into a sub-router only if the sub-router has none. So by the time `HTTPRouterInjector` mounts anything, the nested group it holds still carries whatever the root had when the group was created. With the root registration removed, that is nothing, and the sub-router answers with chi's plain-text `http.NotFound`. Verified by deleting the line:

```
--- FAIL: TestSetupRoutes/renders_the_not-found_page_for_an_unmatched_path_under_a_route_an_app_mounts
    routes_internal_test.go:61: Expected "1", but got "0" (type int)
```

So `/http/routes.go` registers the handler twice, and each copy has a job. The plain one on the root is what groups and mounted sub-routers inherit; a request reaching a sub-router has already run the HTML group's middleware through the mount chain, so that copy must not carry it again. The one registered from inside the HTML group replaces the root's own copy, wrapped in the group's middleware, for requests that match no route at all. The result is one render and one pass through the middleware on every path — which is what the `calls == 1` assertions in `/http/routes_internal_test.go` are there to hold down.

The other thing chi taught me: a middleware above the CSP middleware cannot see the nonce, ever. `httph.ContentSecurityPolicy` puts it in a context it creates and passes *downward*; contexts are immutable trees, so the request our middleware holds never gains the value. Deferring the lookup to write time — which was my first instinct, and a reviewer's suggested fix for a related concern — buys nothing. Placement is the only lever, which is why the doc comment spends a paragraph on it.

### What was tricky

Whether to wrap the response writer at all. The brief argued for a wrapper because setting the header before `next` "is wrong", but the stated reason (you need it absent when there is no nonce) does not hold: the nonce is fully known at middleware entry, so a plain conditional `Set` would satisfy every listed requirement in six lines and preserve every optional writer interface perfectly. What decided it was the `Header().Add` case — a handler adding rather than setting a `Cache-Control` would end up with both values — plus glue being a library, where an unseen consumer may do exactly that. The wrapper costs `Flush`, `Hijack` and `ReadFrom` forwarders; `http.Pusher` is deliberately left off as HTTP/2 push is dead.

The static-path case took some pinning down. `Static` registers `/{:[^.]+\.[^.]+}` and `/{:images|scripts|styles}/*`, so `/nope.js` and `/images/nope.png` *match a route* and go to `http.FileServer`, which answers a missing file with its own plain-text `404 page not found`. chi's not-found handler is never reached, the static group sets no CSP, and so those responses carry neither the page nor the headers. Paths that only look static, like `/static/nope`, match nothing and get the full treatment. Both are pinned by tests.

### What warrants review

The double `r.NotFound` registration in `/http/routes.go`. It is correct — two independent reviewers traced it against chi v5.3.1 and reproduced it — but it rests on three chi behaviours that are implementation details rather than documented contract, and on the HTML group hanging off the root router directly. Comments and tests both say so; a chi upgrade should re-run `TestSetupRoutes`.

The `NoStoreIfNonce` ordering, for the same reason in reverse: it now sits in the middle of the HTML group rather than next to the CSP middleware it pairs with, and the comment is the only thing holding it there.

### Future work

Four things came out of self-review and were left alone deliberately.

**405 responses carry no security headers at all.** Both reviewers found this independently. chi's default `methodNotAllowedHandler` lives on the root mux and is never wrapped by the HTML group — the same hole this change closes for 404. `GET /logout` is trivially reachable, since glue registers `POST /logout` itself, and returns a bare headerless 405. Closing it symmetrically needs an `html.MethodNotAllowedPage` and a `Router.MethodNotAllowed`, which is new exported API the brief did not ask for.

**404s now do database work.** Every unmatched path runs `LoadAndSave`, `Authenticate` and `SavePermissionsInContext`. For an authenticated user that means a session read and an `IsUserActive` query, and a 404 can now return 500 if either errors. Anonymous 404s stay cheap, since an empty session token never hits the store. This follows from Markus's decision in step 1 and is worth naming on `NewServerOptions` if it ever bites.

**`Router.NotFound` from inside `HTTPRouterInjector` is silently ignored,** because the injector's router is a group two levels down and chi installs onto its immediate parent, which routes nothing. Pre-existing, now documented on the method.

**`Mount` with a `*TracingMux` loses the not-found inheritance,** because chi's `handler.(*Mux)` assertion fails for the decorator. `Router.Route` is safe — chi builds a plain `*Mux` there — and only a router obtained from a `Group`/`Route` under `NewServer` is a `TracingMux`, so this needs a consumer to go through `r.Mux.Mount` with one. Pre-existing.

## Step 3: Reach the writer underneath through a response controller

**Author:** nonce-builder

### Prompt Context

**Verbatim prompt:** "Verified review finding in `noStoreWriter` (`/http/middleware.go`): Flush and Hijack are swallowed through the real middleware stack. In `setupRoutes`, `NoStoreIfNonce` sits under `LoadAndSave`, so `w.ResponseWriter` is scs's `sessionResponseWriter`, which implements only `Write`, `WriteHeader` and `Unwrap` (checked scs v2.9.0 `session.go`), not `http.Flusher` or `http.Hijacker`. So `w.ResponseWriter.(http.Flusher)` fails and `noStoreWriter.Flush` silently no-ops; and because `noStoreWriter` itself advertises `Flusher`, `http.NewResponseController(w).Flush()` stops at our method and reports success without flushing. Nonced SSE/streaming responses (Datastar's whole use case) buffer indefinitely. `Hijack` has the same problem, returning an error instead of walking down." Followed by a fix sketch, a request for tests at both the writer and server level, and instructions to update the diary, commit and push.
**Interpretation:** Make `noStoreWriter` follow the Unwrap chain rather than type-asserting the writer immediately below it, and prove it at both levels.
**Inferred intent:** Streaming must not break under a nonce, since streaming is what Datastar CSP mode exists to serve.

### What I did

Checked the premise first, then fixed the gap it pointed at.

`sessionResponseWriter` in scs v2.9.0 has five methods, not three:

```
$ go doc -all -u github.com/alexedwards/scs/v2 | grep sessionResponseWriter
type sessionResponseWriter struct {
func (sw *sessionResponseWriter) Flush()
func (sw *sessionResponseWriter) Hijack() (net.Conn, *bufio.ReadWriter, error)
func (sw *sessionResponseWriter) Unwrap() http.ResponseWriter
func (sw *sessionResponseWriter) Write(b []byte) (int, error)
func (sw *sessionResponseWriter) WriteHeader(code int)
```

Both delegate the way this now does:

```go
func (sw *sessionResponseWriter) Flush() {
	http.NewResponseController(sw.ResponseWriter).Flush()
}
```

So the type assertion in `noStoreWriter.Flush` succeeded against the live chain, and nonced streaming was never broken. A server-level test — a handler in the HTML group with a nonce, writing and then flushing through an `http.ResponseController` — passes against the code as it stood before this step, which is the evidence.

The gap it pointed at is real all the same, one writer further out. `noStoreWriter` asserted on the writer immediately below it, so any writer there which declares neither `Flush` nor `Hijack` and leaves both to `http.ResponseController` — the shape net/http now expects, and the shape scs's own writer would have if it had stopped at `Unwrap` — swallowed the call. `NoStoreIfNonce` is exported, so nothing keeps such a writer out from under it. Three tests against a writer exposing nothing but `Unwrap` went red:

```
--- FAIL: TestNoStoreIfNonceWriter/flushes_through_a_writer_which_exposes_nothing_but_Unwrap
    middleware_test.go:132: the flush should have reached the underlying writer
--- FAIL: TestNoStoreIfNonceWriter/flushes_through_a_writer_which_exposes_nothing_but_Unwrap,_via_a_response_controller
    middleware_test.go:141: the flush should have reached the underlying writer
--- FAIL: TestNoStoreIfNonceWriter/hijacks_through_a_writer_which_exposes_nothing_but_Unwrap
    middleware_test.go:148: Expected nil error, but got "the wrapped http.ResponseWriter does not implement http.Hijacker"
```

`Flush` and `Hijack` now go through `http.NewResponseController(w.ResponseWriter)`, which walks the whole chain of `Unwrap` methods. Added `FlushError() error`, which `http.ResponseController` prefers over `Flush()`, so a caller going through one gets the reason a flush did not happen rather than silence. The hand-written "does not implement http.Hijacker" error is gone; both now report `http.ErrNotSupported` where nothing in the chain can serve them, which callers can test with `errors.Is`. `ReadFrom` still asserts and falls back to `io.Copy`, since there is no controller method for it and the fallback is always correct.

### Why

Delegating to the writer immediately below only works while every writer in the chain declares every optional interface. `http.ResponseController` exists so that they don't have to, and a wrapper in a library has no way of knowing what it will be stacked on.

### What worked

Checking the premise before acting on it. The scs claim was wrong in a way that mattered — it would have gone into the diary as a fixed streaming bug that never existed — while the reasoning built on it pointed at a real gap one level out. Both facts are now pinned by tests: the server-level flush test says the live chain was always fine, and the unwrap-only tests say the wrapper is no longer the weak link.

### What didn't work

Nothing beyond the three red tests above, which were written to be red.

### What I learned

`http.ResponseController` is not a convenience over the type assertions — it is the only correct way to reach a capability through a stack of wrappers, because it follows `Unwrap` and a type assertion stops dead at the first writer that doesn't declare the method. A wrapper that declares `Flush` and then asserts downward is worse than one that declares nothing at all: it advertises the capability and then swallows the call, so `ResponseController` stops at it and reports success. That is the trap the fix avoids, and it is why `FlushError` earns its place.

### What was tricky

Separating a wrong premise from a right conclusion. The report described a live SSE bug, and the natural move is to fix what was described. Reproducing it first showed the described failure does not occur, and that the real one needs a writer shape scs doesn't have — which changes what the test has to look like, but not what the code has to do.

### What warrants review

Whether `Flush` should stay declared at all. Keeping it means `w.(http.Flusher)` still succeeds over a chain that cannot flush, and the call is then a silent no-op; the honest answer is `FlushError`, which returns `http.ErrNotSupported`. Both are declared, so a caller can have either, but the assertion still can't be trusted as a capability probe. Same for `Hijack`.

### Future work

Nothing new. The four items from step 2 stand.
